# 批量任务与交付：从“一张能跑”到“一百张能对账”

单条命令跑通后，下一步通常就是批量。批量的难点不是循环，而是**每项可追溯、失败可隔离、断点可续跑、结果可对账**。

## 1. 什么时候需要这一层

- 同一动作要处理 10 个以上对象。
- 需要无人值守/定时运行。
- 输出要交给别人，必须能说清“哪些成功、哪些失败、为什么”。
- 单张失败不能导致整批重来。

## 2. manifest：唯一的事实来源

用 CSV 或 JSON 描述每项任务，命令行只接收 manifest 路径：

```csv
id,input,output,page_size,scale,expected_pages
S001,projects/a.prj,out/S001.pdf,A1,1:100,1
S002,projects/b.prj,out/S002.pdf,A1,1:100,1
```

规则：

- `id` 唯一、稳定；用它做目录名、日志名、失败现场名。
- `input` 是**副本路径**，不是原件；原件路径另存一列或只在配置里。
- `output` 唯一；不要依赖软件默认命名。
- 把影响结果的参数（图幅、比例、CTB、模板）写进列或配置，不要藏在脚本里。
- manifest 本身记录 hash，运行日志引用它。

## 3. 逐项事务循环

```text
for item in manifest:
    work = _app_work/items/<id>/
    copy(item.input, work/input)
    try:
        result = run_one(work/input, item.options)
        verify(result, item.expected)
        record(id, "ok", result)
    except Exception as exc:
        capture_failure(id, work)
        record(id, "failed", exc)
        if fail_fast: break
```

要点：

- **先复制再执行**：每项独立工作目录，互不污染。
- **验收通过才算成功**：文件存在、非零、页数/图幅/数值符合期望。
- **记录开始/结束时间、耗时、产物大小/hash**；后续对账和性能分析都靠它。
- 循环里不要 `sleep` 等软件；用可观测状态。
- 单实例软件：能一次启动处理多项就一次启动；必须重启的，在 item 之间显式关闭并确认无残留。

## 4. 对账与结果表

输出 `manifest_result.csv`，至少包含：

| 列 | 含义 |
|---|---|
| id | manifest 的 id |
| status | ok / failed / skipped |
| output | 实际产物路径 |
| bytes | 大小 |
| pages | 页数（如适用） |
| sha256 | 产物 hash |
| seconds | 耗时 |
| error | 失败原因（成功留空） |

对账断言：

- manifest 行数 = `ok` + `failed` + `skipped`。
- `ok` 的产物数 = 期望产物数；每个 output 存在且非零。
- 没有重复 id、重复 output、未在 manifest 中的多余产物。
- 失败项都有 error 和失败现场目录。

把对账结果打印成摘要：`ok=97 failed=2 skipped=1`，并列出失败 id。

## 5. 断点续跑与幂等

- 每项完成后写 `done.json`（含输入 hash、产物 hash、时间）；重跑时先读它。
- `--resume` 跳过 `done.json` 且输入 hash 未变的项；输入变了必须重跑。
- 输出已存在且内容一致 → 可跳过；不一致 → 失败或 `--replace` 覆盖，不要静默覆盖。
- 单项命令也要幂等：重复执行同一项，结果一致或明确报“已完成”。

## 6. 失败隔离与重跑

- 默认“继续跑完，最后汇总失败项”；需要立即停就 `--fail-fast`。
- 失败现场按 id 保存：`failures/<id>/{screenshot.png,controls.txt,app.log,params.json}`。
- 提供 `--only <id>` / `--from <id>` 重跑单项；不要为了重跑一张图重跑全批。
- 失败原因分类：输入问题 / 软件问题 / 环境问题 / 超时 / 验收不符；汇总时按类计数。
- 同一项连续失败 3 次就停，不要无限重试。

## 7. 打印/导出的特殊参数

批量出图常见坑：

- 图幅/比例/打印样式（CTB/STB/线宽）可能来自模板，不是命令行；先固定模板并校验。
- 输出格式（PDF/DWG/DXF/TIFF）决定验收方式：PDF 比页数/图幅/文本，DWG 比实体数/图层。
- 多页合并/拆分：确认“一个输入 → 一个输出”还是“一个输入 → 多个输出”；manifest 要能表达一对多。
- 文件名：软件可能自动加后缀/前缀；以最终文件系统结果为准，不要只信界面提示。
- 空图/空白页：页数对但内容空，仍需抽查；可比较文件大小下限或文本/线框数量。
- 打印队列：有队列时轮询“队列清空 + 文件大小稳定”，不要按固定时间等。

## 8. 性能与并发

- 一次启动处理多项通常远快于每项重启；先测“启动成本/单项成本”。
- 单实例/文件锁/许可并发限制的软件只能串行；不要为了快开多个实例。
- 可并行的软件按资源分池（CPU/许可/输出目录），并在日志里记录并发度。
- 记录总耗时、单项均值、P95；批量性能退化时先看是否每项都在重启。

## 9. 交付打包

- 产物目录按 id 或业务命名组织；另附 `manifest_result.csv`、`README`、`SHA256SUMS.txt`。
- 交付包命名带日期/版本；不要覆盖上一版。
- 打包前抽查 3 项：打开正常、页数/图幅正确、与人工样本一致。
- 交付说明写清：输入要求、运行命令、失败怎么重跑、产物在哪。

- [ ] 每项有验收，不是“跑完就算”
- [ ] 有 `manifest_result.csv` 和对账摘要
- [ ] 支持 `--resume`/`--only`，不会整批重跑
- [ ] 失败按 id 保存现场，可单张重跑
- [ ] 打印/导出参数固定并可校验
- [ ] 单实例软件串行，无残留进程
- [ ] 交付包有 README 和 SHA256
